# MCPGoProxy

## Назначение

Если у вас есть информационная система с данными и бизнес-логикой, но сама система ничего не знает о современных LLM и MCP, а вы хотите предоставить эти данные языковой модели, возникает необходимость связать две совершенно разные среды.

С одной стороны находится LLM-клиент — например, LM Studio, Claude, Open WebUI, Cursor или другое приложение, поддерживающее MCP. Он предоставляет языковой модели возможность работать с внешними инструментами, но не знает внутреннего устройства вашей ERP-системы.

С другой стороны находится существующая информационная система — ERP, учетная система или корпоративный сервис. Она уже содержит необходимые данные и бизнес-логику, но не должна знать, какая именно LLM или какой клиент будет к ней обращаться.

**MCPGoProxy предназначен для того, чтобы связать эти два мира.**

Прокси выступает промежуточным MCP-сервером между LLM-клиентом и существующей информационной системой:

```text
┌─────────────────────────────────────────────┐
│              LLM / MCP Clients              │
│                                             │
│  LM Studio   │   Claude   │   Open WebUI    │
│  Cursor      │   VS Code  │   другие MCP    │
│              │            │    клиенты      │
└──────────────────────┬──────────────────────┘
                       │
                       │ MCP
                       ▼
              ┌─────────────────┐
              │                 │
              │   MCPGoProxy    │
              │                 │
              └────────┬────────┘
                       │
                       │ HTTP
                       ▼
              ┌─────────────────┐
              │                 │
              │  ERP / Backend  │
              │                 │
              └─────────────────┘
```
При этом разработчику системы не требуется самостоятельно реализовывать MCP-сервер, разбираться в особенностях конкретных LLM-клиентов или поддерживать отдельную интеграцию для каждой модели.

Достаточно реализовать в своей системе два HTTP-сервиса:

* **`erp_tool_url`** — возвращает описание доступных MCP-инструментов;
* **`erp_call_url`** - выполняет вызов выбранного инструмента и возвращает его результат.

После этого MCPGoProxy преобразует описание инструментов внутренней системы в формат MCP и предоставляет их любому совместимому MCP-клиенту.

Таким образом, существующая система продолжает работать в привычной для её разработчика среде и не получает зависимости от конкретной LLM. Вся специфика взаимодействия с MCP и LLM-клиентами остается на стороне прокси.

Это позволяет разделить ответственность:

* **информационная система** отвечает за данные, бизнес-логику, права доступа и выполнение операций;
* **MCPGoProxy** отвечает за протокол MCP и передачу вызовов между LLM-клиентом и системой;
* **LLM-клиент** предоставляет инструменты языковой модели и организует взаимодействие с ней.

В результате подключение LLM к существующей системе сводится к реализации небольшого HTTP-интерфейса на стороне самой системы, без необходимости погружаться в устройство MCP и особенности конкретных моделей.

## Возможности

* подключение LLM-клиентов к ERP через MCP;
* получение динамического списка инструментов из ERP;
* динамическое формирование MCP `inputSchema`;
* поддержка вложенных объектов и массивов в параметрах инструментов;
* передача вызовов MCP-инструментов в HTTP-сервис ERP;
* получение структурированных JSON-результатов от ERP;
* работа через STDIO;
* работа через Streamable HTTP для клиентов с HTTP-подключением к MCP;
* передача авторизационных данных ERP через HTTP-заголовок Authorization.
* обязательная аутентификация запросов к ERP через ERP_API_KEY.

## Транспорты

MCPGoProxy поддерживает два режима работы:

* **STDIO** — MCPGoProxy запускается MCP-клиентом как дочерний процесс и взаимодействует с ним через `stdin/stdout`;
* **Streamable HTTP** — MCPGoProxy самостоятельно запускается как HTTP-сервер, к которому MCP-клиент подключается по HTTP.

Режим работы определяется параметром командной строки.

### STDIO

STDIO предназначен прежде всего для локальных приложений, которые умеют запускать MCP-сервер как дочерний процесс.

Типичные клиенты:

* LM Studio;
* Kilo Code;
* Cursor;
* Claude;
* другие MCP-клиенты с поддержкой STDIO.

Запуск:

```text
mcp_server.exe
```

или явно:

```text
mcp_server.exe --stdio
```

В этом режиме MCPGoProxy не запускает HTTP-сервер. MCP-клиент взаимодействует с прокси непосредственно через `stdin/stdout`.

### Streamable HTTP

Streamable HTTP предназначен для MCP-клиентов, которые подключаются к уже запущенному MCP-серверу по HTTP.

Например:

* Open WebUI;
* другие MCP-клиенты с поддержкой MCP Streamable HTTP.

Запуск:

```text
mcp_server.exe --http
```

После запуска MCP-сервер будет доступен по адресу:

```text
http://127.0.0.1:40242/mcp
```

## Конфигурация

Конфигурация MCPGoProxy хранится в файле `config.json`, расположенном рядом с исполняемым файлом.

Конфигурация используется независимо от выбранного режима транспорта.

```json
{
    "erp_tool_url": "http://<addr>/<http_service>/hs/ai/mcpTools",
    "erp_call_url": "http://<addr>/<http_service>/hs/ai/mcpCall",
    "http_host": "127.0.0.1",
    "http_port": 40242,
    "disable_localhost_protection": true
}
```

### Параметры конфигурации

* **erp_tool_url** - HTTP endpoint ERP для получения списка доступных MCP-инструментов и их описаний
* **erp_call_url** - HTTP endpoint ERP для выполнения вызова выбранного инструмента
* **http_host** - Адрес, на котором MCPGoProxy запускает HTTP-сервер
* **http_port** - Порт HTTP-сервера MCPGoProxy
* **disable_localhost_protection** - Отключает проверку localhost для HTTP-сервера. Может потребоваться при подключении клиентов, работающих в Docker или другой изолированной среде
* **http_host**, **http_port** и **disable_localhost_protection** используются только в режиме `--http`.

### HTTP API ERP

Для работы MCPGoProxy информационная система должна предоставить два HTTP endpoint:

**`erp_tool_url`** — возвращает список доступных MCP-инструментов, их описания и параметры.

**`erp_call_url`** — принимает вызов выбранного инструмента, передает его в информационную систему и возвращает результат.

Таким образом, стороне ERP не требуется реализовывать MCP-сервер. Достаточно предоставить два обычных HTTP-сервиса, а преобразованием их интерфейса в MCP занимается MCPGoProxy.

## Формат описания MCP-инструментов

Endpoint `erp_tool_url` должен возвращать JSON с описанием доступных инструментов ERP.

MCPGoProxy использует этот ответ для динамического формирования MCP-инструментов. Поэтому ERP не должна самостоятельно формировать MCP-схему — достаточно вернуть описание инструментов в формате, который понимает MCPGoProxy.

### Общая структура

Корневой объект JSON содержит набор инструментов.

Ключ каждого свойства — уникальное имя инструмента, которое будет использоваться в MCP.

Каждый инструмент содержит:

* `description` — описание назначения инструмента;
* `parameters` — описание входных параметров инструмента.

Пример:

```json
{
    "ping_erp": {
        "description": "Проверка связи с ERP.",
        "parameters": {
            "rand_param": {
                "type": "integer",
                "description": "Случайное число",
                "required": true
            }
        }
    }
}
```

Если инструмент не имеет входных параметров, `parameters` можно не указывать:

```json
{
    "get_server_time": {
        "description": "Получить текущее время сервера."
    }
}
```

### Описание параметра

Каждый параметр описывается объектом со следующими свойствами:

* `type`- Тип параметра
* `description` - Описание назначения параметра
* `required` - Признак обязательности параметра
* `ItemType` - Тип элементов массива (для массивов простых значений)
* `items` - Описание полей объекта, являющегося элементом массива (для массивов объектов)

Поддерживаются следующие типы:

* `string`
* `integer`
* `number`
* `boolean`
* `array`

### Простые параметры

Для параметров простых типов достаточно указать `type`:

```json
{
    "vehicle_number": {
        "type": "string",
        "description": "Государственный номер автомобиля.",
        "required": false
    },
    "limit": {
        "type": "number",
        "description": "Максимальное количество записей.",
        "required": false
    }
}
```

Параметр считается обязательным, если `required` имеет значение `true`.

### Массив простых значений

Для массива значений простого типа используется `type: "array"` и `itemType`.

Например, массив строк:

```json
{
    "fields": {
        "type": "array",
        "itemType": "string",
        "description": "Имена полей, которые необходимо вернуть.",
        "required": true
    }
}
```

`itemType` определяет тип каждого элемента массива.

### Массив объектов

Если элементами массива являются объекты со структурой из нескольких полей, используется `items`.

Например, массив периодов:

```json
{
    "periods": {
        "type": "array",
        "description": "Массив периодов отбора данных.",
        "required": true,
        "items": {
            "date_from": {
                "type": "string",
                "description": "Дата начала периода (YYYY-MM-DD).",
                "required": true
            },
            "date_to": {
                "type": "string",
                "description": "Дата окончания периода (YYYY-MM-DD).",
                "required": true
            }
        }
    }
}
```

В этом случае каждый элемент `periods` должен иметь структуру:

```json
{
    "date_from": "2026-09-01",
    "date_to": "2026-09-30"
}
```

### Вложенные структуры

Описание параметров поддерживает вложенные структуры.

Например, массив групп условий:

```json
{
    "filter_groups": {
        "type": "array",
        "required": false,
        "description": "Массив групп условий.",
        "items": {
            "inside_logic": {
                "type": "string",
                "required": true,
                "description": "Логика объединения условий внутри группы."
            },
            "conditions": {
                "type": "array",
                "required": true,
                "description": "Условия отбора.",
                "items": {
                    "field": {
                        "type": "string",
                        "required": true,
                        "description": "Имя поля."
                    },
                    "operator": {
                        "type": "string",
                        "required": true,
                        "description": "Оператор сравнения."
                    },
                    "value": {
                        "type": "string",
                        "required": true,
                        "description": "Значение для сравнения."
                    }
                }
            }
        }
    }
}
```

Такая структура преобразуется MCPGoProxy в соответствующую вложенную JSON Schema.

### Рекомендации по описаниям

`description` является частью интерфейса инструмента, который получает LLM. Поэтому описание должно объяснять не только технический тип параметра, но и **как и когда его следует использовать**.

Хорошее описание:

```text
Государственный номер автомобиля. Используй его, если пользователь попросил показать перевезенный груз по конкретному автомобилю.
```

Менее полезное описание:

```text
Номер автомобиля.
```

Для инструментов также рекомендуется в `description` указывать:

* назначение инструмента;
* когда его следует использовать;
* какие другие инструменты необходимо вызвать перед ним;
* ограничения и важные правила использования;
* требования к параметрам;
* особенности интерпретации результата.

### Пример полного ответа

Endpoint `erp_tool_url` может вернуть, например:

```json
{

        "description": "Проверка связи с ERP.",
        "parameters": {
            "rand_param": {
                "type": "integer",

                "required": true
            }
        }
    },
    "get_server_time": {
        "description": "Получить текущее время сервера."
    },
    "get_transported_cargo": {
        "description": "Получить данные о перевезённом грузе за указанные периоды.",
        "parameters": {
            "periods": {
                "type": "array",
                "description": "Массив периодов отбора данных.",
                "required": true,
                "items": {
                    "date_from": {
                        "type": "string",
                        "description": "Дата начала периода (YYYY-MM-DD).",
                        "required": true
                    },
                    "date_to": {
                        "type": "string",
                        "description": "Дата окончания периода (YYYY-MM-DD).",
                        "required": true
                    }
                }
            },
            "vehicle_number": {
                "type": "string",
                "description": "Государственный номер автомобиля.",
                "required": false
            }
        }
    }
}
```

Таким образом, ERP предоставляет **описание доступных функций в собственном формате**, а MCPGoProxy автоматически преобразует это описание в MCP `tools` и соответствующие `inputSchema`.

Это позволяет добавлять, изменять и удалять инструменты на стороне ERP без изменения исходного кода MCPGoProxy.


### API-ключ ERP

Для авторизации запросов к ERP MCPGoProxy использует переменную окружения `ERP_API_KEY`.

Переменная окружения является **обязательной**. При запуске MCPGoProxy проверяет её наличие. Если ключ не задан, прокси не запускается.

Полученный ключ MCPGoProxy передаёт в каждый запрос к ERP через HTTP-заголовок:

```text
Authorization: <значение ERP_API_KEY>
```

MCPGoProxy **не анализирует и не изменяет содержимое этого значения**. Поэтому ERP может самостоятельно определить используемый механизм авторизации.

Например, можно использовать собственный формат API-ключа:

```text
Authorization: ApiKey 4795A142-965D-46B2-8024-59DF7B08B855
```

либо стандартную HTTP Basic Authentication:

```text
Authorization: Basic <Base64(логин:пароль)>
```

Для Basic Authentication значение формируется из строки:

```text
логин:пароль
```

которая кодируется в Base64:

```text
Authorization: Basic Base64(логин:пароль)
```

Например, если логин — `user`, а пароль — `password`, в заголовок передаётся:

```text
Authorization: Basic dXNlcjpwYXNzd29yZA==
```

MCPGoProxy при этом не знает и не должен знать, используется ли API-ключ, Basic Authentication или другой формат. Его задача — передать значение `ERP_API_KEY` в заголовке `Authorization` без изменений.

Проверка авторизации полностью выполняется на стороне ERP.

Таким образом, ответственность разделена следующим образом:

* **MCPGoProxy** — проверяет наличие `ERP_API_KEY` и передаёт его в запросах;
* **ERP** — проверяет валидность ключа, определяет права доступа и возвращает соответствующую ошибку при отказе в авторизации.

`ERP_API_KEY` не хранится в `config.json` и не передаётся через параметры командной строки.

#### Windows PowerShell

Перед запуском MCPGoProxy задайте переменную окружения:

```powershell
$env:ERP_API_KEY="ApiKey 4795A142-965D-46B2-8024-59DF7B08B855"
```

После этого можно запустить MCPGoProxy:

```powershell
mcp_server.exe
```

Для HTTP-режима:

```powershell
mcp_server.exe --http
```

#### LM Studio

Если MCP-клиент запускает MCPGoProxy как дочерний процесс, переменную окружения можно передать через конфигурацию клиента:

```json
{
    "mcpServers": {
        "GoMCPProxy": {
            "command": "D:\\mcp_server.exe",
            "env": {
                "ERP_API_KEY": "ApiKey 4795A142-965D-46B2-8024-59DF7B08B855"
            }
        }
    }
}
```

#### Windows Service

При запуске MCPGoProxy как Windows Service переменная `ERP_API_KEY` должна быть задана в окружении процесса службы.

Конкретный способ задания переменной зависит от способа установки и управления Windows Service.

> **Важно:** `ERP_API_KEY` содержит секрет для доступа к ERP. Не помещайте действующий ключ в `config.json`, исходный код или публичные репозитории.


## Пример подключения к LM Studio

В конфигурации MCP-клиента LM Studio:

```json
{
    "mcpServers": {
        "GoMCPProxy": {
            "command": "D:\\mcp_server.exe",
            "env": {
                "ERP_API_KEY": "ApiKey ..."
            }
        }
    }
}
```

## Пример подключения к Open WebUI

Для Open WebUI используется транспорт `streamable-http`.

MCPGoProxy запускается как HTTP-сервер, после чего MCP-сервер добавляется в Open WebUI как MCP Streamable HTTP connection.

```text
mcp_server.exe --http
```

Конкретный URL MCP endpoint зависит от настроек HTTP-сервера MCPGoProxy.

## Разработка

Проект написан на Go.

Для сборки:

```powershell
go build -o mcp_server.exe
```

Для запуска:

```powershell
.\mcp_server.exe
```

Конфигурационный файл `config.json` должен находиться рядом с исполняемым файлом.
